下面这版按“以当前 JAX 代码为准”的口径，重新整理 RTIP-MD / RTIP pathway workflow。原来的前 6 步更准确地对应 **synthesis RTIP pathway sampling**：先把已选分子构造成分离初态，再用 attractive RTIP 把它们推向一个动态重叠目标。它不完全等同于 `run_rtip_nvt_md` 这个 NVT MD 入口，也不包含完整的反应网络调度层。

**RTIP-MD 详细 Workflow**

**1. 准备候选分子列表**

从论文或算法层面看，体系可以先有一组 candidate molecules，例如：

- `CH2O`
- `H2O`
- `OH-`
- `Ca2+`
- 或后续人为加入的中间体，如 glycolaldehyde、glyceraldehyde、aldotetrose 等

但要和当前 JAX 版代码区分清楚：`rtip_jax` 目前没有实现“每轮从候选列表中随机选 2 个或 3 个分子、允许重复选择”的上层网络采样器。当前代码要求调用者已经决定本轮要合成哪些分子，并把它们显式传给 synthesis/layout 或 pathway workflow。

JAX 里对应的输入方式主要有两种：

```text
rtip-jax synthesize --inputs 1.xyz 2.xyz [3.xyz 4.xyz] --output IS.xyz --dist 5.0 --seed 0
```

或使用已经合并好的结构文件，并手动给出分子原子索引：

```text
rtip-jax synthesize --input input.xyz --mol-index "0,1;2,3" --output IS.xyz --dist 5.0 --seed 0
```

代码层面对应：

```text
rtipmd/jax/src/rtip_jax/cli.py
  parse_mol_index(...)
  _read_xyz_molecules(...)
  _synthesis_input_from_args(...)

rtipmd/jax/src/rtip_jax/pes/bias.py
  SynthesisPot(initial_state, mol_index, para, ...)

rtipmd/jax/src/rtip_jax/workflows/synthesis.py
  _normalize_mol_index(...)
```

这里的 `mol_index` 是当前 JAX 版最关键的“已选分子”表达方式。`_normalize_mol_index` 要求正好有 **2、3 或 4 个非空分子组**，每个组是一组原子下标。Rust 示例入口 `rtipmd/rust/src/lib.rs` / `lib_3mol.rs` 也是先硬编码或拼出 `mol_index`，再调用 `synthesis(..., 5.0)`；并不是自动从 candidate pool 抽样。

因此如果要复现论文中“多轮随机抽候选分子”的完整 reaction-network sampling，需要在 JAX 包外再写一层调度器：负责维护 candidate list、抽样、必要时复制重复分子、生成输入 XYZ / `mol_index`，然后调用当前 JAX 的 synthesis/pathway API。

**2. 构造初始构型 `Pini`**

当前 JAX 版用 `synthesize_layout(system, mol_index, dist, key=...)` 构造分离初态。它的作用是把调用者选中的 2/3/4 个分子先各自平移到自身几何中心为原点，再随机旋转，最后放到固定的几何 offset 上。

代码主线：

```text
rtipmd/jax/src/rtip_jax/workflows/synthesis.py
  synthesize_layout(...)
  synthesis_offsets(...)
  random_rotation(...)
```

具体步骤是：

1. 用 `System.read_xyz` 读取 XYZ。XYZ 文件里的坐标是 Angstrom，读入后会转换成 JAX 内部的 Bohr。
2. 如果使用 `--inputs`，`cli.py::_read_xyz_molecules` 会按文件顺序拼接所有分子，并自动生成 `mol_index`。
3. 对每个分子，代码取该分子的 `molecule_coord`，减去 `jnp.mean(molecule_coord, axis=0)`，也就是减去几何中心。
4. 每个分子使用显式 JAX PRNG key 生成一个随机旋转矩阵；这让 Python 端可复现，但随机流不与 Rust 的 `ndarray-rand` 逐位一致。
5. 旋转后的分子被放到 `synthesis_offsets(n_molecules, dist)` 给出的 offset。

2 个分子的 offset 是：

```text
[-dist, 0, 0]
[ dist, 0, 0]
```

3 个分子的 offset 是平面三角形；4 个分子的 offset 是四面体顶点。注意：从代码看，`dist` 是放置 offset 的数值，不是所有情况下“两分子之间的直接距离”。例如 2 个分子时，两个分子几何中心的距离是 `2 * dist`。

还要特别注意单位边界。`System.coord` 内部是 Bohr，而 `synthesize_layout` 直接把传入的 `dist` 用作内部坐标 offset；CLI 的 `--dist 5.0` 没有额外做 Angstrom 到 Bohr 的转换。原文里常写 “5 Å separation”，但在当前 JAX 代码说明里应更谨慎地写成“`dist=5.0` 的 synthesis 布局参数”；如果要严格把 5 Angstrom 当作几何长度，需要在调用前显式换算成 Bohr。

`Pini` 在当前代码里就是 `SynthesisPot.initial_state` 或 CLI 生成的 `IS.xyz`：

```text
Pini = synthesize_layout(system, mol_index, dist, key)
```

真实势能 `Eini` 不是 `synthesize_layout` 里计算的。进入 `run_rtip_synthesis_path_sampling` 后，第 1 步调用 `real_pes.get_energy_force(s)` 得到第一帧真实势能；代码把它记录为 `pot_real_initial`。

**3. 构造目标构型 `Pdes`**

RTIP synthesis 的目标构型不是固定产物，也不是过渡态，而是一个运行时构造的虚拟目标。JAX 里对应函数是：

```text
rtipmd/jax/src/rtip_jax/workflows/synthesis.py
  synthesis_target_state(system, mol_index)
```

它做的事情是：对每个被选中的分子，保持分子内部相对构型不变，只把该分子的几何中心平移到所有选中原子的共同几何中心。可以写成：

```text
origin_all = mean(selected_coord)
origin_i   = mean(molecule_i_coord)
target_i   = molecule_i_coord - origin_i + origin_all
```

这就是原文中的 `Pdes = centroid-coincided / overlapped configuration`。

有两个代码细节很重要：

- 如果 `mol_index` 覆盖了整个体系，`synthesis_target_state` 返回完整体系 target，后续 RTIP 力直接作用在全体系坐标上。
- 如果体系里还有未参与合成的环境原子或分子，函数只返回选中分子的 fragment target，并返回 active indices。后续 `Rtip0PES` 的 fragment force 会 scatter 回完整体系。

另外，synthesis pathway 的 `Pdes` 是 **每一步根据当前构型动态重建** 的。调用点在：

```text
rtipmd/jax/src/rtip_jax/workflows/pathway_sampling.py
  _synthesis_rtip_bias(...)

rtipmd/jax/src/rtip_jax/workflows/md.py
  _synthesis_md_bias(...)
```

这和 `AttractivePot(final_state=...)` 不一样。`AttractivePot` 是把初态拉向一个调用者给定的固定 final state；`SynthesisPot` 则是把分离反应物拉向“当前几何中心重合”的虚拟目标。

**4. 计算旋转/平移不变距离**

当前 JAX 版 RTIP 距离实现在：

```text
rtipmd/jax/src/rtip_jax/core/rtip.py
```

核心函数包括：

```text
_center_coords(...)
_quaternion_system_matrix(...)
rti_dist(...)
rti_dists(...)
rti_dists_vecs(...)
rti_weight(...)
rti_pot(...)
rti_pot_force(...)
```

它先对两个构型去平移，即分别减去几何中心：

```text
centered1 = coord1 - mean(coord1)
centered2 = coord2 - mean(coord2)
```

然后用 quaternion method 构造 `4 x 4` 实对称矩阵，并调用：

```text
jnp.linalg.eigh(system_matrix)
```

得到 4 个本征值和 4 个本征向量。代码中距离是：

```text
d_k = sqrt(max(eigval_k, 0.0))
```

这里要以当前代码为准：旧的迁移说明里曾写过没有 eigenvalue clamp，但现在 `core/rtip.py` 的 `_sqrt_psd_eigvals` 已经对微小负本征值做了 `maximum(eigvals, 0.0)`，避免数值噪声导致开方失败。

`rti_dist(coord1, coord2)` 返回最小的 RTI distance；`rti_dists(coord1, coord2)` 返回 4 个 eigenmode 的距离。`rti_dists_vecs` 还会把 4 个本征向量转换成旋转矩阵，并返回对齐后的残差向量，用于力表达式。

RTIP 的权重仍然是 Rust 语义：

```text
w_k = 1 / d_k^7
W   = sum_k w_k
```

然后 Gaussian RTIP 能量使用 4 个距离的加权平均：

```text
u_k = a * exp(-d_k^2 / (2 * sigma^2))
E_RTIP = sum_k (w_k / W) * u_k
```

这里保留了 `1 / d^7` 的奇异性：如果距离精确为 0，可能出现 `inf` 或 `nan`。这也是为什么 `Pdes` 只是虚拟目标，实际 workflow 不能简单假设完全重合时数值一定稳定。

**5. 叠加 Gaussian-type attractive RTIP**

在 synthesis pathway 中，JAX 使用 `Rtip0PES` 表示 RTIP bias。虽然名字里有 `local_min`，但这个 dataclass 同时服务于 repulsive、attractive 和 synthesis 场景；吸引或排斥主要由振幅符号决定。

Synthesis attractive RTIP 的构造位置：

```text
rtipmd/jax/src/rtip_jax/workflows/pathway_sampling.py
  _synthesis_rtip_bias(...)
```

代码等价于：

```text
final_state, indices = synthesis_target_state(system, mol_index)
sigma_min = rti_dist(final_state.coord, current_selected_coord)

bias_pes = Rtip0PES(
    local_min = final_state,
    nearby_ts = (),
    a_min = -para.a0 * step,
    a_ts = 0.0,
    sigma_min = sigma_min,
    sigma_ts = (),
)
```

负号是关键：

```text
a_min = -a0 * step
```

因此 Gaussian bias 是 attractive potential；随着 `step` 增大，吸引强度线性增强。默认参数来自 `Para()`：

```text
a0          = 0.002
max_step    = 1500
pot_climb   = 0.185
pot_drop    = 0.02
pot_epsilon = 0.00005
f_epsilon   = 0.001
```

每一步真实 PES 和 bias PES 会分别给出能量和力：

```text
pot_real, force_real = real_pes.get_energy_force(s)
pot_bias, force_bias = bias_pes.get_energy_force(current)

pot_total   = pot_real + pot_bias
force_total = force_real + force_bias
```

当前生产级真实 PES provider 是 `DeepMDPES`；`CP2K` 在 JAX 版里只保留 legacy boundary 文档，不是已实现的 JAX provider。测试和 smoke run 里还会使用 `HarmonicPES`。

还要区分 pathway 和 MD：

- `run_rtip_synthesis_path_sampling` 使用一维线搜索 `min_1d_real_bias`，沿 `force_total` 方向找下一步坐标。
- `run_rtip_nvt_md` 使用 leapfrog 积分和 Berendsen thermostat，是另一条 MD 工作流。

还要注意当前 CLI 暴露的 `rtip-jax deepmd-pathway` 构造的是 `RepulsivePot`，用于 RTIP/IDWM repulsive pathway；它不是 synthesis pathway 子命令。真正的 synthesis pathway 需要直接调用 Python API `run_rtip_synthesis_path_sampling`，或使用仓库中的专门 runner 脚本。

所以原草稿里“propagate_or_optimize”在 JAX synthesis pathway 中更准确应写成：

```text
dcoord = min_1d_real_bias(
    real_pes,
    bias_pes,
    current,
    force_total,
    pot_real + pot_bias,
    para.pot_epsilon * natom,
)
s = s.with_coord(s.coord + dcoord)
```

**6. 迭代推进，并用 `pot_climb` / `pot_drop` 控制 bias 和停止**

这一点最需要按代码修正。当前 JAX 里不是简单的：

```text
En - Eini > Eclimb
Emax - En > Edrop
```

而是使用 `Para.pot_climb` 和 `Para.pot_drop`，并且以 `pot_real_max` / `pot_real_min` 的状态机为准。

Synthesis pathway 的停止逻辑在：

```text
rtipmd/jax/src/rtip_jax/workflows/pathway_sampling.py
  synthesis_stop_decision(...)
```

每一步会先计算真实势能和真实力：

```text
pot_real, force_real = real_pes.get_energy_force(s)
f_real = norm(force_real)
```

然后更新状态：

```text
pot_real_max = max(previous_max, pot_real)
pot_real_min = min(previous_min, pot_real)
pot_real_initial = pot_real if step == 1 else previous_initial
```

`pot_drop` 的作用不是直接判定“成功”，而是关闭 RTIP bias：

```text
if pot_real < pot_real_max - para.pot_drop and pot_real > pot_real_initial:
    add_bias = False
```

这里 synthesis 比 repulsive pathway 多了一个条件：

```text
pot_real > pot_real_initial
```

也就是说，代码希望看到体系曾经从初态爬高，再从高点明显下降；如果只是掉到初态以下，不会按 synthesis drop 逻辑关闭 bias。

关闭 bias 以后，workflow 继续在同一个循环里跑。此时 `_synthesis_rtip_bias` 返回 `ZeroPES`、`pot_bias = 0`、`force_bias = 0`，一维线搜索就退化成真实 PES 上的局部优化。真正停止条件是：

```text
if (not add_bias) and norm(force_real) / sqrt(natom) < para.f_epsilon:
    stop_converged
```

`pot_climb` 则是过度爬坡停止条件，但它相对的是历史最低真实势能 `pot_real_min`，不是初始能量 `Eini`：

```text
if pot_real > pot_real_min + para.pot_climb:
    stop_pot_climb
```

还有一个安全停止条件：

```text
if f_bias > 1000.0:
    stop_large_bias_force
```

因此更贴近 JAX 代码的理解是：

- `pot_drop`：检测真实 PES 从历史高点下降，满足 synthesis 额外条件后 **关闭 RTIP**。
- `f_epsilon`：bias 关闭后真实力 RMS 足够小，才认为本次 pathway 收敛停止。
- `pot_climb`：如果真实势能相对历史低点爬得过高，提前停止。
- `f_bias > 1000`：bias 力过大时提前停止。
- `PathwayResult` 只返回 `system`、`history`、`stopped`；代码没有内建 `success/failed/product` 分类，也不会自动构建 reaction network。

另外一个细节：JAX pathway 的日志和停止判断使用的是本步坐标上的 `pot_real` / `force_real`。代码先计算 `dcoord`，再记录本步状态，最后执行 `s = s.with_coord(s.coord + dcoord)`；更新后的坐标会在下一步重新评估。

**前 6 步的代码校准版伪代码**

```pseudo
# 外层候选分子抽样目前不在 rtip_jax core/CLI 内；
# 调用者先准备 selected molecule files 或 mol_index。

system, mol_index = read_inputs_or_combined_xyz(...)

Pini = synthesize_layout(
    system,
    mol_index,
    dist = user_dist,
    key = PRNGKey(seed),
)

config = SynthesisPot(
    initial_state = Pini,
    mol_index = mol_index,
    para = Para(...),
)

s = config.initial_state
state = SynthesisSamplingState()

for step in 1..para.max_step:

    pot_real, force_real = real_pes.get_energy_force(s)
    f_real = norm(force_real)

    Pdes, active_indices = synthesis_target_state(s, mol_index)
    sigma_min = rti_dist(Pdes.coord, selected_current_coord)

    if state.add_bias:
        bias_pes = Rtip0PES(
            local_min = Pdes,
            nearby_ts = (),
            a_min = -para.a0 * step,
            a_ts = 0.0,
            sigma_min = sigma_min,
            sigma_ts = (),
        )
        pot_bias, force_bias = bias_pes.get_energy_force(current)
    else:
        bias_pes = ZeroPES()
        pot_bias = 0
        force_bias = 0

    force_total = force_real + force_bias

    dcoord = min_1d_real_bias(
        real_pes,
        bias_pes,
        current,
        force_total,
        pot_real + pot_bias,
        para.pot_epsilon * natom,
    )

    state, stopped, decision = synthesis_stop_decision(
        state,
        step = step,
        pot_real = pot_real,
        f_real = norm(force_real),
        f_bias = norm(force_bias),
        natom = s.natom,
        para = para,
    )

    log(step, pot_real, pot_bias, sigma_min, decision)
    s = s.with_coord(s.coord + dcoord)

    if stopped:
        break
```

**7. bias 关闭后回到真实 PES**

原草稿里的“成功后移除 RTIP，回到真实 PES”在 JAX 代码中对应 `add_bias=False`。一旦 `synthesis_stop_decision` 判定 `bias_off_after_synthesis_drop`，下一步 `_synthesis_rtip_bias` 会返回：

```text
pot_bias = 0.0
force_bias = zeros_like(system.coord)
bias_pes = ZeroPES()
```

随后 workflow 仍然使用同一个 `min_1d_real_bias` 更新坐标，只是 bias 贡献已经为零。它没有单独调用一个名为 `local_optimize_on_real_pes` 的函数；真实 PES 局部优化是通过“bias 关闭后的同一套一维搜索循环”完成的。

输出层面，workflow 会在 `write_outputs=True` 时写：

```text
rtip.pdb
rtip.out
```

或者由脚本重命名成作业号前缀文件。API 返回 `PathwayResult.system` 作为最终结构，但当前 JAX core 不会自动写 `product.xyz`，也不会自动标注该结构是不是化学意义上的产物。

**8. 检测键变化并记录反应类型**

论文中的 formose 体系会关注某些键变化，例如：

- `C-C`：aldol / retroaldol
- `C-H`：enolization，尤其是羰基 alpha-C 去质子化
- `H-H`：H2 形成
- `O-O`：通常不是有效主反应

也会弱化一些不希望主导网络增长的变化，例如：

- `C-Ca`
- `H-Ca`
- `O-Ca`
- `Ca-Ca`
- `C-O`
- `H-O`

但这些属于反应网络分析层，不是当前 JAX RTIP core 的控制逻辑。`Rtip0PES` 并不知道哪些键应该形成或断裂；它只看结构到虚拟目标的 RTI distance，并输出 Gaussian bias 力。当前 JAX 版没有通用的 bond-change classifier，也没有自动给 pathway 标注 aldol、retroaldol、enolization 等类型。

仓库里有一些 research 脚本会对特定体系做距离/结构分析，例如 `research/ic5c02384/scripts/analyze_bias_exploration_1tbu_co2.py`，但那是应用层分析，不是 `rtip_jax` 的通用 workflow 能力。若要把 formose 网络真正跑起来，需要额外实现：

```text
trajectory / final structure
  -> bond perception
  -> bond-change comparison
  -> reaction type labeling
  -> product deduplication
  -> candidate pool update
```

**9. 多轮并行采样，构建反应网络**

从算法层面，每次 pathway sampling 可以独立运行，所以适合并行采样。大量 trial 之后，可以把成功路径中的反应物、产物、中间体和键变化整理成 reaction network。

但当前 JAX 工程层的边界是：

- core workflow 是普通 Python 控制流，不包含 MPI fan-out。
- Rust 中随机旋转/扰动用 MPI broadcast 保持 rank 同步；JAX 版改为显式 JAX PRNG key，MPI 行为没有直接迁移。
- `research/ic5c02384/scripts/slurm/run_deepmd_rtip.slurm` 可以提交独立 Slurm 作业，适合做工程上的多作业并行。
- `rtip_jax` 没有内建 reaction network 数据结构、候选池更新、产物去重或微观动力学模拟。
- 当前生产级真实 PES provider 是 DeePMD；CP2K 只保留历史边界文档。

因此，JAX 版已经实现了“单次给定分子组的 synthesis/pathway/MD 核心”，但论文级“自动发现并扩展反应网络”的外层系统仍需要在其上方补齐。

**一句话版**

按当前 JAX 代码，synthesis RTIP pathway 的主线应写成：

```text
显式给定 2/3/4 个分子或 mol_index
→ synthesize_layout 构造分离初态 Pini
→ SynthesisPot 保存 Pini 和 mol_index
→ 每一步用 synthesis_target_state 从当前构型动态构造虚拟 Pdes
→ core/rtip.py 计算 RTI 距离、4 个 eigenmode 权重和 Gaussian RTIP
→ 用 a_min = -a0 * step 形成 attractive bias
→ E_total / F_total = real PES + bias PES
→ pathway 模式沿总力做一维线搜索更新坐标
→ pot_drop 关闭 bias，f_epsilon 收敛停止，pot_climb 或过大 bias 力提前停止
→ 输出 PDB 和标量日志；反应判别、产物去重、候选池更新属于外层分析/调度
```

这份检查结果的核心结论是：**你现在要对照的 JAX 代码实现，不是论文里完整的 RTIP-MD reaction-network workflow，而是其中“给定分子组的一次 synthesis RTIP pathway sampling 核心”。** 所以前面那版按论文讲的 workflow 需要收窄口径，否则会把外层调度、候选池抽样、键变化分类、反应网络构建等还没实现的部分误认为在 JAX core 里。

我认为这份检查结果里最重要的 6 个校正点是：

1. **候选分子抽样不在当前 JAX core 内**
   当前代码不是“自动从 candidate pool 随机抽 2/3 个分子”，而是要求调用者显式给 `--inputs` 或 `mol_index`。
   所以代码对照时，第一层应看 `mol_index` 如何表达已选分子，而不是找 reaction-network sampler。

2. **`Pini` 的构造是 `synthesize_layout`，但 `dist` 有单位/语义风险**
   记录里指出：XYZ 读入后坐标转成 Bohr，但 `synthesize_layout(..., dist)` 直接把 `dist` 当内部坐标 offset 用。
   这是一个关键坑。`--dist 5.0` 不一定严格等于论文里的 `5 Å separation`，而且 2 分子时中心距是 `2 * dist`。后面对照代码或复现实验时，这个参数必须单独确认。

3. **`Pdes` 是动态虚拟目标，不是产物/TS**
   这是理解 synthesis RTIP 的关键。JAX 里 `synthesis_target_state(system, mol_index)` 每一步根据当前构型重建目标，把选中分子的几何中心拉到共同中心。
   因此它和 `AttractivePot(final_state=...)` 那种固定终态吸引不同。

4. **RTI distance 实现细节已经偏代码化**
   检查结果明确到 `core/rtip.py`：中心化、quaternion matrix、`eigh`、4 个 eigenmode、`1/d^7` 权重、Gaussian 加权。
   特别值得注意的是本征值 clamp：`sqrt(max(eigval, 0))`。这说明当前 JAX 代码已经处理了微小负本征值的数值问题，但 `1/d^7` 在 `d=0` 附近仍可能有奇异风险。

5. **attractive RTIP 的符号来自 `a_min = -a0 * step`**
   这点很适合对照代码。`Rtip0PES` 不是单纯“吸引势”的类名，而是靠振幅符号决定吸引/排斥。
   synthesis pathway 中负号是关键，且强度随 `step` 线性增强。

6. **停止逻辑不是论文式 `Eclimb/Edrop` 的简单翻译**
   这是最重要的修正。JAX 里不是：
   ```text
   En - Eini > Eclimb
   Emax - En > Edrop
   ```
   而是：
   - `pot_drop`：从历史高点下降足够多后关闭 bias；
   - 还要求 `pot_real > pot_real_initial`；
   - bias 关闭后，真实力 RMS 小于 `f_epsilon` 才收敛停止；
   - `pot_climb` 是相对历史最低点 `pot_real_min`，不是相对初始能量；
   - `f_bias > 1000` 是安全停止。

所以这份检查结果的判断方向是对的：**论文 workflow 是算法概念层，JAX workflow 是单次 pathway implementation 层。拿去对照代码时，应以 JAX 的状态机、动态 `Pdes`、`Rtip0PES` bias 构造和 `synthesis_stop_decision` 为主线。**

还需要注意一个边界：我当前工作目录下没有这份记录中提到的 `rtipmd/jax/src/rtip_jax/...` 代码树，所以我无法在本机直接逐行验证这些路径和函数实现。但就这份检查记录本身来看，它已经把“论文描述”和“当前 JAX 实现”的差异抓得比较准，尤其是 `dist`、`pot_drop`、`Pdes dynamic` 和“没有内建反应网络层”这几处。

## 2026-05-31 补充：RTIPMD 温度控制在 JAX 代码中的已有信息

本次已在当前工作目录实际核对 `rtipmd/jax/src/rtip_jax/...` 代码。下面这部分专门整理 RTIPMD 的温度、动能、thermostat 和初始速度控制。

**1. 温控参数入口**

核心参数在 `rtipmd/jax/src/rtip_jax/config.py` 的 `Para` 中：

```text
dt        = 0.5      # fs
tau       = 500.0    # Berendsen coupling time
temp_bath = 1000.0   # K
```

`dt`、`tau`、`temp_bath` 会随 `Para` 传入 `run_rtip_nvt_md(...)`。MD 参数校验目前只显式检查：

```text
max_step >= 0
print_step > 0
dt > 0
tau > 0
```

也就是说，当前核心代码没有单独检查 `temp_bath > 0`。实际研究脚本通常把 `temp_bath` 设为 `300.0`，例如 `run_rcmd.py`、`run_bias_exploration_1tbu_co2.py` 默认都是 300 K；核心包默认值仍是 1000 K。

**2. 质量、动能和温度公式**

位置：`rtipmd/jax/src/rtip_jax/workflows/md.py`

`atom_masses(system)` 从 `System.atom_type` 读取元素，再调用 `atomic_mass(element)` 得到原子单位质量。温度计算依赖这些质量，因此没有 `atom_type` 或元素质量不在支持表内会失败。

动能相关函数：

```text
twice_kinetic_energy(v, m) = sum_i m_i * |v_i|^2
kinetic_energy(v, m)      = 0.5 * twice_kinetic_energy(v, m)
```

瞬时温度公式：

```text
T = (sum_i m_i * |v_i|^2) * HARTREE_TO_JOULE
    / (BOLTZMANN * 3.0 * (natom - 1))
```

这里有几个细节：

- 用的是 `sum_i m_i |v_i|^2`，不是 `0.5 * sum_i m_i |v_i|^2`。
- 自由度写成 `3 * (natom - 1)`，等价于扣掉整体平动的 3 个自由度。
- 但代码没有在每一步显式移除质心速度，只是在温度分母中使用了 `natom - 1`。
- 单原子体系会直接报错：`temperature requires at least two atoms`，避免 `3 * (natom - 1)` 除零。

**3. Berendsen thermostat**

函数：`berendsen_lambda(temp, para)`

```text
temp = max(temp, 1.0)

lambda = sqrt(
    1.0 + (para.dt / para.tau) * (para.temp_bath / temp - 1.0)
)
```

关键行为：

- 在算缩放因子前，温度有 `1.0 K` floor，避免极低温时除零或缩放爆炸。
- `dt / tau` 是耦合强度。默认 `dt=0.5 fs`、`tau=500 fs`，所以 `dt/tau=0.001`，温控很弱，`thermo_lambda` 通常非常接近 1。
- 当 `T < temp_bath` 时，`lambda > 1`，速度被放大，相当于加热。
- 当 `T > temp_bath` 时，`lambda < 1`，速度被缩小，相当于冷却。
- 这不是随机 thermostat，也不是 Nose-Hoover/Langevin，只是确定性的速度重缩放。

**4. Leapfrog 中 thermostat 的作用位置**

`run_rtip_nvt_md(...)` 每一步大致顺序是：

```text
coord_new, velocity_half = leapfrog_first(coord, velocity, acceleration, para)
temp_half = temperature(velocity_half, masses)
lambda_scale = berendsen_lambda(temp_half, para)

pot_real, force_real = real_pes.get_energy_force(s)
pot_bias, force_bias = _md_bias(config, s, step)
force_total = force_real + force_bias
acceleration = force_total / masses

velocity = leapfrog_second(velocity_half, acceleration, lambda_scale, para)
temp = temperature(velocity, masses)
kin = kinetic_energy(velocity, masses)
```

也就是说，`lambda_scale` 用半步速度 `velocity_half` 的温度计算，然后在第二个 half step 更新速度后统一乘上去：

```text
v_{n+1} = (v_{n+1/2} + 0.5 * dt_au * a_{n+1}) * lambda
```

这里的 `dt` 输入单位是 fs，积分时通过 `FEMTOSECOND_TO_AU` 转成原子时间单位。

**5. 高温时的 bias 反馈**

当前 `md.py` 中除了 Berendsen thermostat，还有一个额外的温度反馈：

```text
if temp_half > 1500.0:
    temp_scale = 1500.0 / temp_half
    pot_bias *= temp_scale
    force_bias *= temp_scale
    f_bias *= temp_scale
```

这不是 thermostat 本身，而是对 RTIP/RC bias 的安全限幅：半步温度超过 1500 K 时，把 bias 能量和 bias 力按 `1500 / T` 缩小。它不会直接缩放真实 PES 力，也不会直接改速度；速度仍由 Berendsen 的 `lambda` 控制。

这个机制意味着温控有两层：

- Berendsen：始终对速度做弱重缩放，目标是 `temp_bath`。
- Bias temperature feedback：只在 `temp_half > 1500 K` 时削弱人工 bias 注入。

**6. 初始速度控制**

核心 `run_rtip_nvt_md(...)` 的默认行为：

```text
initial_velocity is None     -> zeros_like(coord)
initial_acceleration is None -> zeros_like(coord)
```

因此核心 MD 默认是零初速度。如果 `perturb=True`，只会对初始坐标加随机扰动；不会自动采样 Maxwell-Boltzmann 速度。

CLI 层：

- `rtip-jax mock-md` / `deepmd-md` 调用 `run_rtip_nvt_md(...)` 时没有传 `initial_velocity`，所以也是零初速度。
- `--no-perturb` 只控制是否坐标扰动，不控制速度采样。

研究脚本层额外加了定向初速度：

- `research/ic5c02384/scripts/run_rcmd.py`
- `research/ic5c02384/scripts/run_bias_exploration_1tbu_co2.py`
- `research/ic5c02384/scripts/run_guided_rtipmd_1tbu_co2.py`

这些脚本用 `_direction_velocity(...)` 把“当前结构指向 target / synthesis target 的方向”归一化成指定 `initial_temp` 的初速度。公式反过来使用核心温度公式：

```text
twice_kinetic = initial_temp * BOLTZMANN * 3.0 * (natom - 1) / HARTREE_TO_JOULE
velocity = direction * sqrt(twice_kinetic / sum_i m_i |direction_i|^2)
```

并且脚本会先减去质量加权平均方向，使初始速度方向不含整体平动。

`run_bias_exploration_1tbu_co2.py` 还提供 `--zero-velocity`：此时传 `initial_velocity=None`，回到核心默认的零初速度；这个选项是为了更接近 Rust 原版 RTIPMD。

**7. 输出和测试覆盖**

MD 输出行 `MDStep` 会记录：

```text
temp
temp_bath
thermostat_lambda
kin
```

`rtip.out` 表头包含：

```text
temp_K  temp_bath_K  thermo_lambda  kin_Ha
```

这使得每步都能直接观察当前温度、目标浴温、Berendsen 缩放因子和动能。Pathway workflow 没有速度自由度，所以 pathway 的 `temp_K` / `kin_Ha` 是 `nan`；只有 `run_rtip_nvt_md` 的温度是真正由速度和质量算出来的。

测试中已有覆盖：

- `tests/test_md_helpers.py`：质量、动能、温度公式、单原子报错、Berendsen 低温 floor、加速度、leapfrog。
- `tests/test_md_workflow.py`：MD 能跑通，`temp_bath` 会写进 history，输出表头包含 `temp_K` 和 `thermo_lambda`。

**8. 当前判断**

当前 JAX RTIPMD 的温控可以概括为：

```text
零初速度或外层脚本指定初速度
→ leapfrog 更新坐标和半步速度
→ 用半步速度算瞬时温度
→ Berendsen lambda 控制速度重缩放
→ 若 T_half > 1500 K，额外削弱 bias 力
→ 记录最终速度对应的 temp_K / kin_Ha / thermo_lambda
```

它的控制能力偏弱，尤其默认 `tau=500 fs` 时 `dt/tau=0.001`，所以如果 bias 快速注入能量，温度可能会明显高于 `temp_bath` 并持续一段时间。此前小体系 CO2 反应里的高温振荡，和这个弱 Berendsen 耦合、自由度少、bias 注入快的组合是一致的。
